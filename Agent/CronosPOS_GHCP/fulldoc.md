### 2.2 Genesis / Config Initialisation — automatic, nothing to do

**No manual data seeding.** The StatefulSet runs three init containers, in this order:

| # | Container | What it does |
|---|---|---|
| 1 | `restore-snapshot` | Discovers the current Polkachu pruned snapshot (the filename rotates daily), streams it straight into the PVC with `curl \| lz4 -d \| tar -x`, and verifies `blockstore.db` / `state.db` / `application.db` landed. ~9 GB, about 5 min. |
| 2 | `install-chain-maind` | Downloads the upstream v8.0.0 release binary, verifies its SHA256 against upstream `checksums.txt`, and fetches mainnet `genesis.json`. |
| 3 | `configure` | Runs `chain-maind init`, installs genesis, and patches `config.toml` / `app.toml` — seeds, persistent peers, pruning, and the API/gRPC listeners. |

The tarball is **streamed, never staged**, so the PVC needs no download+extract peak.

**Re-restoring or adopting existing data** — both are env switches on `restore-snapshot`.
Never mount the PVC from a throwaway pod to fix state by hand; that routes around the guard
that protects real chain data from an init-container `rm -rf`.

| Env var | Effect |
|---|---|
| `FORCE_RESTORE=<new value>` | Wipe and re-pull the snapshot. A **token, not a boolean** — the value is recorded on the volume once honoured, so leaving it set cannot cause a re-wipe loop. Change the value to force again. |
| `ADOPT_EXISTING=true` | Treat chain data already on the volume as legitimate and use it as-is. Writes only the sentinel; **never deletes**. This is the switch for a prod-data migration. |

```bash
kubectl set env statefulset/node-cronospos -n cronospos -c restore-snapshot FORCE_RESTORE=redo-1
```

An interrupted restore needs neither — it marks its own work with `.restore-in-progress` and
clears it automatically on the next start.

## 4b. RPC Verification — proving the node actually works

`kubectl get pods` showing `Running 1/1` proves almost nothing. A node can be Running, Ready,
and syncing nothing at all. These checks go from "is the process alive" to "is it serving real
chain data", in order. Stop at the first one that fails — that is your fault line.

The container is `alpine` with busybox: it has **`wget`, no `curl` and no `jq`**. On Windows,
write **`curl.exe`** — bare `curl` is a PowerShell alias for `Invoke-WebRequest`.

> **Keep commands short.** Long pasted lines get mangled by some terminals (spaces and `$`
> silently dropped). Run one short command, then use **up-arrow** to repeat it rather than
> re-pasting.

### Step 1 — Is the process alive?

```bash
kubectl exec -n cronospos node-cronospos-0 -c chainmaind -- wget -qO- http://localhost:26657/health
```

`{"jsonrpc":"2.0","id":-1,"result":{}}` = the RPC server is answering.

**This does NOT mean synced.** CometBFT's `Health` handler returns an empty `200`
unconditionally and never inspects sync state (`rpc/core/health.go`). It is exactly what the
readiness probe uses, which is why `Ready 1/1` is not evidence of sync.

### Step 2 — Right chain, right version?

```bash
kubectl exec -n cronospos node-cronospos-0 -c chainmaind -- wget -qO- http://localhost:26657/abci_info
```

Expect `"data":"chain-maind"` and `"version":"v8.0.0"`. The version **must** match the live
network, or the node will sync until the next upgrade height and then halt on a mismatched app
hash — a node that looks healthy and is permanently stuck. Compare against a public node:

```bash
curl.exe -s https://rpc.mainnet.crypto.org/abci_info
```

### Step 3 — Connected to the network?

```bash
kubectl exec -n cronospos node-cronospos-0 -c chainmaind -- sh -c "wget -qO- http://localhost:26657/net_info | head -c 200"
```

Read `n_peers`. **Zero peers means it can never sync** — check egress on TCP 26656.
One or two is too thin and will stall; `persistent_peers` is what keeps it healthy (see §8).

### Step 4 — Is it actually advancing? *(the one that matters)*

```bash
kubectl exec -n cronospos node-cronospos-0 -c chainmaind -- wget -qO- http://localhost:26657/abci_info
```

Run it, wait 60s, press **up-arrow**, run again. Compare `last_block_height`.

| Delta over ~60s | Meaning |
|---|---|
| **> 60** | Catching up healthily (chain speed is only ~12/min) |
| **~12** | At the tip — done |
| **0** | Stalled. Same height *and* same `last_block_app_hash` confirms it. |

A single reading tells you nothing. Two readings is the whole test.

### Step 5 — How far behind?

```bash
kubectl exec -n cronospos node-cronospos-0 -c chainmaind -- sh -c "wget -qO- http://localhost:26657/status | head -c 900"
curl.exe -s https://rpc.mainnet.crypto.org/status
```

Compare `sync_info.latest_block_height` on each. `catching_up` flips to `false` at the tip.
Cronos POS blocks are ~5.08s, so gap ÷ 12 = minutes of chain time behind.

### Step 6 — Is the APP layer serving, not just consensus?

This is the step people skip, and it is the one that catches a half-configured node. Consensus
can be perfectly healthy while the REST and gRPC listeners were never enabled.

```bash
kubectl exec -n cronospos node-cronospos-0 -c chainmaind -- wget -qO- http://localhost:1317/cosmos/base/tendermint/v1beta1/syncing
```

`{"syncing":false}` = the REST API on 1317 is up **and** the node reports itself synced.

```bash
kubectl exec -n cronospos node-cronospos-0 -c chainmaind -- sh -c "wget -qO- http://localhost:1317/cosmos/bank/v1beta1/supply | head -c 200"
```

Returns the `basecro` total supply. If this answers, the ABCI application is genuinely queryable
— state is readable, not just blocks arriving.

```bash
kubectl exec -n cronospos node-cronospos-0 -c chainmaind -- sh -c "wget -qO- http://localhost:1317/cosmos/staking/v1beta1/pool | head -c 200"
```

Staking pool totals — another live app-state read.

### Step 7 — Historical queries (proves the restored data is intact)

```bash
kubectl exec -n cronospos node-cronospos-0 -c chainmaind -- sh -c "wget -qO- 'http://localhost:26657/block?height=31400000' | head -c 300"
```

Pick a height **above** your snapshot's restore point (`cat /chain-home/.snapshot-restored`).
Below the pruning window this correctly returns an error — that is not a fault, this node runs
`pruning = "custom"`, keeping only the last 100 states.

```bash
kubectl exec -n cronospos node-cronospos-0 -c chainmaind -- sh -c "wget -qO- http://localhost:26657/validators | head -c 300"
```

### Step 8 — Mempool and consensus liveness

```bash
kubectl exec -n cronospos node-cronospos-0 -c chainmaind -- wget -qO- http://localhost:26657/num_unconfirmed_txs
```

Returns `n_txs` / `total_bytes`. Proves the mempool reactor is running. `0` is normal on a quiet
chain — it should be *present*, not necessarily non-zero.

```bash
kubectl exec -n cronospos node-cronospos-0 -c chainmaind -- sh -c "wget -qO- http://localhost:26657/consensus_state | head -c 300"
```

### Step 9 — From outside the cluster, through the Internal LB

```bash
kubectl get svc node-cronospos-rpc-lb -n cronospos -o jsonpath='{.status.loadBalancer.ingress[0].ip}'
```

Then, from anything on the VNet — note the **remapped** LB ports:

```bash
curl.exe -s http://<ILB-IP>:1332/status        # Tendermint RPC  (container 26657)
curl.exe -s http://<ILB-IP>:2332/cosmos/base/tendermint/v1beta1/syncing   # REST (container 1317)
```

gRPC on `3332` (container 9090) has no plain-HTTP probe; test it with `grpcurl` from a client
that has it, or just confirm the listener:

```bash
kubectl exec -n cronospos node-cronospos-0 -c chainmaind -- sh -c "netstat -ltn | grep -E '26656|26657|1317|9090'"
```

All four should be listening on `0.0.0.0`. Anything bound to `127.0.0.1` is unreachable from a
Service — that is a config fault, not a network one.

### Pass criteria — all of these

| # | Check | Pass |
|---|---|---|
| 1 | `/health` | returns `{}` |
| 2 | `/abci_info` version | `v8.0.0`, matching the live network |
| 3 | `n_peers` | `> 0`, ideally 5+ |
| 4 | height delta over 60s | `> 12` |
| 5 | `catching_up` | `false` once caught up |
| 6 | `/cosmos/bank/v1beta1/supply` | returns `basecro` |
| 7 | `/block?height=<recent>` | returns a block |
| 8 | listeners | 26656/26657/1317/9090 on `0.0.0.0` |
| 9 | logs | no `wrong Block.Header.AppHash`, `CONSENSUS FAILURE`, or `panic` |

```bash
kubectl logs node-cronospos-0 -n cronospos -c chainmaind --tail=4000 | grep -Ei "AppHash|CONSENSUS FAILURE|panic|OOMKilled"
```

Empty output is the pass.

## 5. Auto-Disk Config (pvc-watcher)


The `pvc-watcher` CronJob runs every 15 minutes (`*/15 * * * *`) in the `pvc-watcher` namespace. It monitors disk usage and auto-expands the PVC when usage exceeds 80%.


### NODE_CONFIG line — copy this into the ConfigMap


```
# Format: "NAMESPACE|POD|MOUNT_PATH|PVC_NAME|THRESHOLD|INCREMENT_GI|MAX_SIZE_GI"
"cronospos|node-cronospos-0|/chain-home|node-cronospos-data|80|100|500"
```


### Add to live cluster


**Option A — kubectl edit (interactive):**
```bash
kubectl edit configmap pvc-watcher-script -n pvc-watcher
# Add the line above into the NODE_CONFIG array inside the ConfigMap data
```


**Option B — kubectl patch (scripted):**
```bash
# First, get the current value:
kubectl get configmap pvc-watcher-script -n pvc-watcher -o jsonpath='{.data.NODE_CONFIG}'


# Then patch — append the new entry to the existing array.
# Replace <existing-entries> with all current entries:
kubectl patch configmap pvc-watcher-script -n pvc-watcher --type=merge -p \
  '{"data":{"NODE_CONFIG":"<existing-entries>\n\"cronospos|node-cronospos-0|/chain-home|node-cronospos-data|80|100|500\""}}'
```

## 6. Teardown


Remove resources in reverse order to avoid dependency errors:


```bash
kubectl delete -f 04-service.yaml
kubectl delete -f 03-statefulset.yaml
kubectl delete -f 02-pvc.yaml
kubectl delete -f 01-storageclass.yaml
kubectl delete -f 00-namespace.yaml
```


> ⚠️ **The underlying Azure Disk (PV) is NOT deleted automatically** because `reclaimPolicy: Retain`.  
> To fully remove the disk, after teardown:
> 1. Run `kubectl get pv | grep node-cronospos` to find the PV name.
> 2. Run `kubectl delete pv <pv-name>` to release the K8s resource.
> 3. Delete the Azure Disk manually in the Azure Portal or via CLI:
>    ```bash
>    az disk delete --name <disk-name> --resource-group <rg-name> --yes
>    ```


Also remove the pvc-watcher NODE_CONFIG line:
```bash
kubectl edit configmap pvc-watcher-script -n pvc-watcher
# Remove the line: "cronospos|node-cronospos-0|/chain-home|node-cronospos-data|80|100|500"
```

## 8. Node-Specific Notes


- **Image version:** `v8.0.0` is pinned. Check [Crypto.com Chain releases](https://github.com/crypto-org-chain/chain-main/releases) before upgrading — chain upgrades require governance proposals and coordinated restarts.
- **Cosmos SDK port rule:** Ports `26656`, `26657`, `1317`, and `9090` are fixed by the Cosmos SDK protocol. They must never be remapped or changed in the container args or service `targetPort`.
- **IP Sharing:** Several Services may share one LB frontend IP **only if their port sets are
  disjoint**. Every Cosmos chain defaults to 26657/1317/9090, so chains left on standard ports
  collide and the Service sticks in `SyncLoadBalancerFailed`. This node's RPC LB deliberately
  uses **1332/2332/3332** as frontend ports, which makes its port set disjoint and therefore
  *shareable*. `targetPort` stays the real container port, so the node itself is untouched.
- **Disk sizing:** A full Cronos PoS chain sync requires significant disk space. Monitor usage early and ensure pvc-watcher is active. The max is set to `500Gi` — increase `--pvc-max` if needed.
- **Memory:** The default `4Gi` memory limit may be tight during initial sync under load. Monitor with `kubectl top pod node-cronospos-0 -n cronospos` and raise the limit if OOMKilled events occur.
- **Probes:** All three hit CometBFT's `/health` on `26657`, **not** a TCP check on `26656`. A
  TCP probe on the P2P port reports healthy through a total freeze, because the listener never
  closes. Liveness additionally tests **height progress** and restarts only after a 30-minute
  stall.
- **`Ready` does not mean synced.** CometBFT's `/health` returns an empty `200` unconditionally
  and never inspects sync state (`rpc/core/health.go`). Judge sync from
  `/status .sync_info.catching_up` and the height gap — never from the pod's Ready column.
- **Peering:** `seeds` alone is **not** sufficient. A CometBFT seed answers one PEX request and
  disconnects by design, so a seeds-only node holds 1-2 peers, drains them, and blocksync
  stalls with the height frozen. `persistent_peers` are re-dialed and kept — that is what makes
  sync steady. Refresh the list from any public RPC's `/net_info` if peer count stays low.
